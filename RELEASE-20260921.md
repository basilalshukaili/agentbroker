## What IS in this branch now

**1. `43cb6dd` + `b332e25`** — unchanged from the previous pass: tool-count
single source of truth (`core/tool_auth.py`), and `/keys/request` no longer
returning a false `200 verification_sent` when no email was sent.

**2. `7d4e406` — Ownership propagation.** Every write-tool handler
(`call_business`, `escalate_to_human`, `send_transactional_confirmation`,
`send_message`) received an authenticated `agent_id` and dropped it before
storing the operation receipt, so every receipt was unowned and
`status_outcome.py`'s read policy let ANYONE holding an `operation_id` read
it back. `get_conversation`'s own guard let a row with no recorded owner
through, and the MCP dispatcher never bound a caller onto `send_message` in
the first place, so every conversation opened through MCP was exactly such a
row — any caller holding, or guessing (`reference` is four decimal digits
scoped by a public `business_number`), a conversation id or operation id
could read another agent's messages, bookings and call transcripts.
`core/ownership.py` is now the one place the read rule lives; every write
handler and REST route threads `agent_id` through to storage; unowned rows
are now denied to everyone rather than admitted to anyone.

**3. `e7d5907` — Booking path: truthful success, calendar-destination
binding, cancellation authorization.** Four defects in the Cal.com path,
fixed together because they share the same code:
   - A Cal.com `PENDING` booking (awaiting the business's own acceptance)
     was reported `appointment_confirmed`, and a missing provider booking id
     fell back to a locally-generated uuid — both charged. Success now
     requires a real provider id AND an accepted/confirmed provider status.
   - **An imported business's booking could land on the founder's own
     single-tenant Cal.com calendar** while the receipt named the business
     the caller asked for, because the code asked the one connected account
     for "any usable event type." `resolve_event_type_id_for_business()`
     now binds an event type only when the business's own booking URL
     resolves to a Cal.com page the connected account actually hosts;
     otherwise the booking is refused (`booking_destination_unmapped`)
     before any request reaches Cal.com. This was a cross-tenant data/
     booking leak, not only an honesty issue, and was not named in the
     original blocked-work list — found while reviewing `calcom.py`'s diff
     for this pass.
   - Upstream failures (`get_availability` 503/timeout, `book_slot`/
     `cancel_booking` timeout or 5xx) were reported as confident, CHARGED
     successes ("0 slots available", "nothing was booked"). They now raise,
     and the new `BookingOutcomeUnknown` distinguishes "provably nothing
     happened" from "we cannot tell" — the latter is `OperationStatus.
     UNKNOWN`, uncharged, and explicitly not retriable (retrying an unknown
     outcome risks a second real booking).
   - **Cancellation authorization.** `adapter.cancel_booking` was called
     against a caller-supplied appointment id with nothing verifying the
     caller had any claim to that booking — any agent holding or guessing a
     Cal.com uid could cancel a different agent's customer's appointment.
     `schedule_appointment.py` now looks up the appointment's recorded
     owner (keyed by the provider's own booking id, via the new
     `get_appointment_owner_async`) and applies the same fail-closed
     `read_denial` policy before calling Cal.com at all.
   - The async/Celery path (`reliability/async_runner.py`) gets the
     identical honesty gate rather than a second, independently-drifting
     copy — it imports `_choose_slot`/`_CONFIRMED_PROVIDER_STATES` directly
     from `core.schedule_appointment`.

**4. `e140bf3` — Retry safety.** The idempotency gate advertised in
README/well-known was not actually wired to prevent a duplicate execution:
a durable record was written only AFTER a tool call finished, so two
concurrent calls with the same key both ran the real tool, and a process
killed mid-flight left no trace for the next retry to see. `claim()` now
writes a durable `pending` marker BEFORE dispatch (atomically, via
`storage/idempotency_store.py`'s `reserve()`), `complete()`/`release()`
resolve it, and a genuinely concurrent duplicate gets an explicit
`idempotency_in_progress` refusal instead of running twice. Terminal writes
for a confirmed booking, a cancellation, or an `UNKNOWN` outcome are now
awaited durably (`set_complete_durable`) instead of fire-and-forgotten.

**5. `d88f443` — Widened the dead-monkeypatch guard** beyond the single
hardcoded path it was written to catch, to a general scan for
`monkeypatch.setattr`/`patch` calls that target a name a consumer already
imported eagerly (and therefore holds its own snapshot of). Committed last
because its self-consistency check verifies allowlist entries against test
files this pass's other commits introduce.

**6. `0d65092` — Fix found by this pass's own CI verification.**
Running the full suite against a clean worktree of the branch (see below)
surfaced one pre-existing test, `tests/unit/test_hostile_tool_results_do_
not_steer.py::test_an_inbound_reply_cannot_pose_as_a_turn`, that stubbed an
UNOWNED conversation row and read it with no identity — exactly the hole
commit `7d4e406` closes, so the test now failed for the right reason
(`KeyError('messages')`, because the call is correctly refused). The test
now gives its stub row a real owner and calls with that owner's identity,
so it again exercises what it was written to prove (a hostile inbound
message cannot pose as a system turn) through a call shape that is
actually reachable post-fix. This was **not** in the original blocked-work
list — it is the kind of dependency that only surfaces by actually running
the suite, which is exactly what this step of the task asked for.

## Un-applied database migrations

Both are **written and described, NOT applied** — per this task's hard
rule, no migration was run against Supabase.

- **`migrations/operations_table.sql`** adds an `appointment_id` column
  (the provider's own booking id) to `operations`, which
  `get_appointment_owner_async` (the cancellation-authorization lookup)
  reads. **Until this is applied**: the column does not exist, so every
  Supabase-fallback lookup in `get_appointment_owner_async` finds nothing
  and returns `None` — the ownership check then fails closed (denies the
  cancel) for any appointment whose owner cannot be found in the in-memory
  store on the process handling the cancel request. In practice this means
  cross-process/cross-restart cancellations of real bookings may be
  incorrectly refused (not incorrectly allowed) until this migration is
  applied. Apply it before or during the deploy that ships `e7d5907`, via
  the Supabase SQL editor for the project at `SUPABASE_URL` (same mechanism
  as `migrations/enable_rls.sql`).
- **`migrations/idempotency_keys_claim_status.sql`** adds the `status`
  column and the unique constraint that makes a durable idempotency claim
  atomic ACROSS processes (the application-level `claim()` already fully
  protects same-process concurrency and the sequential crash-then-restart
  case without this migration). **Until this is applied**: the
  `insert_row`/`update_row` calls in `agent_interface/idempotency_gate.py`
  still work (the table's pre-existing columns are untouched), but two
  separate processes claiming the identical idempotency key in the same few
  milliseconds could both win — a real but narrow race, reduced by the
  application-level fix but not eliminated until this constraint exists.

## How to deploy this branch (when you decide to)

Unchanged mechanism from the previous pass: Production (`api.hatchloop.dev`)
is a Render blueprint (`deploy/render.yaml`, service `smb-broker`,
`runtime: docker`) that auto-deploys on push to `main`. There is no separate
deploy script.

1. Apply the two migrations above via the Supabase SQL editor (ideally
   right before the deploy below, so the code that reads the new column
   ships close to the column existing — the code fails closed either way,
   so ordering is not safety-critical, only correctness-of-cancellation-
   during-the-gap-critical).
2. Review all 8 commits (`43cb6dd` through `0d65092`) against `main`.
3. Merge (or fast-forward) `main` to include them, then push `main`.
   Render's blueprint builds `deploy/Dockerfile` automatically.
4. The Cloudflare edge worker (`hatchloop.dev/mcp/agent-broker`) serves
   cached snapshots independently of the Render origin and is untouched by
   this release — no edge redeploy is required.

### Verify success after deploying

- `curl -fsS https://api.hatchloop.dev/health` → `200`.
- **Ownership — get_conversation now requires identity.** Call
  `get_conversation` via the MCP endpoint with NO `X-Agent-Identity` header
  (any `conversation_id`): expect a receipt with `reason_code
  "identity_required"`, not a conversation body. Before this release the
  same call could return another agent's messages.
- **Ownership — get_status/get_outcome deny unowned operations.** Poll
  `get_status`/`get_outcome` for an operation created with NO identity, from
  a DIFFERENT caller (or none): expect `status: "forbidden"` /
  `reason_code` naming `_owner_unknown` or `not_your_operation`, not the
  receipt. Before this release the receipt was returned to anyone holding
  the `operation_id`.
- **Cancellation authorization.** Attempt `schedule_appointment` with
  `action: "cancel"` and an `existing_appointment_id` created by a
  DIFFERENT `X-Agent-Identity`: expect a denial (`reason_code
  "not_your_appointment"` or `"appointment_owner_unknown"`), and confirm
  directly with Cal.com that the booking was NOT cancelled. Before this
  release the cancellation would have gone through.
- **Booking honesty (passive — verify on the next real booking).** A
  successful `schedule_appointment` receipt's `result` now includes
  `calcom_event_type_id` and `provider_status`; if Cal.com is slow or
  returns a non-2xx during a real booking attempt, expect `reason_code
  "booking_outcome_unknown"` (status `unknown`, `cost.amount: 0`) rather
  than a false confirmation or a false "nothing was booked."
- `curl -s https://api.hatchloop.dev/keys/request -X POST -H 'Content-Type: application/json' -d '{"email":"you@example.com"}'`
  → `503 {"error":"onboarding_unavailable", ...}` while `RESEND_API_KEY`
  remains unset (unchanged from the previous pass's note).
- Run the CI workflow itself on the push (GitHub Actions on `main`) and
  confirm the `verify` job is green — expect the SAME single CRLF-artifact
  behavior described below if anyone re-runs the suite locally on Windows;
  the Ubuntu runner will not see it.

### Roll back

**A plain `git revert` of the ownership/booking-path/cancellation-
authorization commits (`7d4e406`, `e7d5907`, `e140bf3`, `0d65092`) — or a
Render rollback to a build from before this deploy — WOULD REOPEN both
holes named at the top of this file: the anonymous/wrong-caller read of
operation receipts and conversations, and the unauthenticated cancellation
of any business's booking.** Do not treat rollback of this release as a
neutral, safe default the way the previous pass's 2-commit rollback was
(reverting `43cb6dd`/`b332e25` alone remains safe — neither implements an
authorization check).

If a rollback is needed for an unrelated reason (a bug this release
introduced, a bad interaction in production), the safe path is:
1. **Roll forward with a fix**, not backward — write and ship a small
   corrective commit on top, keeping the ownership/cancellation checks in
   place. This is almost always possible because the checks are additive
   refusals (deny cases that were previously wrongly allowed); a bug in
   them is far more likely to be an over-broad denial (annoying, safe) than
   an under-broad one.
2. If a genuine emergency rollback of the whole deploy is unavoidable,
   roll back to a build **at or after `e7d5907`** (never to `6cb7b8a` or
   earlier) — this keeps ownership propagation and cancellation
   authorization in place even if the retry-safety or dead-monkeypatch
   commits need to come out.
3. Whatever is rolled back, treat the two holes as OPEN again immediately,
   notify whoever needs to know, and re-ship as the next priority — do not
   let "we rolled back for an unrelated reason" quietly become "the holes
   are closed in production" in anyone's head.
