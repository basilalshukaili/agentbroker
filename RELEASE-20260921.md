# Release 2026-09-21 — branch `security/honesty-release-20260921`

## Read this first

**This branch does NOT close the ownership-propagation or the
unauthenticated-cancellation vulnerabilities.** Those two fixes exist in the
working tree (uncommitted) but could not be safely committed this session —
see "What is NOT in this branch" below. Production remains exposed to:

- anonymous/wrong-caller reads of `get_status`/`get_outcome`/`get_conversation`
  receipts (the "ownership propagation" hole), and
- an unauthenticated caller cancelling **any** booking (the
  "cancellation-authorization" hole).

Nothing in this branch makes that worse, and nothing in this branch is a
prerequisite the still-open holes depend on. But do not read "CI is green" or
"the security release shipped" as "the holes are closed." They are not.

## What IS in this branch (2 commits)

1. **`43cb6dd` — Tool-count consistency in `core/tool_auth.py`.** One source
   of truth for which of the 23 tools need a key, replacing six surfaces
   (`web/facts.py`, `web/pages.py`, `agent_interface/well_known.py`,
   `registry/servers.yaml`, and the `smithery.yaml`/`server.json`/`glama.json`
   catalogues generated from it) that each answered the question themselves
   and drifted.
2. **`b332e25` — Onboarding honesty.** `POST /keys/request` now returns
   `503 onboarding_unavailable` instead of a false `200 verification_sent`
   when no email actually left the process (production has no Resend key
   configured today, so this was firing on every real signup). Six
   discovery/doc surfaces stopped pointing integrators at `/auth/token`
   (an internal, admin-only route that 401s for every outside caller) and
   now describe the real `/keys/request` flow.

Both are documentation/honesty fixes. Neither adds or removes an
authorization check. Full detail and verification notes are in each commit
message; the classification of all ~78 originally-dirty files is in the
session's chat report, not duplicated here.

## What is NOT in this branch, and why

Three fixes from today's session (**ownership propagation**, **booking
success honesty**, **async worker containment / cancellation
authorization**) all run through `core/schedule_appointment.py`,
`agent_interface/mcp_server.py`, `storage/outcome_store.py`, and
`channels/direct_api/calcom.py`. All four files were confirmed, empirically,
to be under active concurrent edit by a different agent this session
(retry-safety / idempotency work, labelled "Assignment #8" in that agent's
own new test files) — mtimes moving minutes apart across the session, one
file's content changing again between two checks 17 minutes apart, and the
retry-safety files' own code explicitly noting "owned by a concurrent agent
this session."

This is not just a timing coincidence — it is a **hard runtime dependency**:

- `storage/outcome_store.py`'s committed (HEAD) `set_pending`/`set_complete`
  do not accept an `agent_id` parameter at all. The ownership fix's other
  files (`core/status_outcome.py`, `core/call_business.py`,
  `core/escalate_to_human.py`, `core/send_transactional_confirmation.py`,
  `core/send_message.py`) all call `set_complete(..., agent_id=agent_id)`.
  Committing those without the in-flight `storage/outcome_store.py` change
  would raise `TypeError: unexpected keyword argument 'agent_id'` on every
  booking, call, escalation and confirmation — a production outage, not a
  security fix.
- `core/get_conversation.py`'s stricter read guard (deny an unowned
  conversation to everyone, not just to a mismatched caller) depends on
  `agent_interface/mcp_server.py` binding the caller's identity when it opens
  a conversation. `mcp_server.py`'s dispatcher is one of the in-flight files.
  Shipping the stricter guard without that binding would make every
  MCP-opened conversation permanently unreadable — even by its rightful
  owner — since HEAD's dispatcher never records one.
- `reliability/async_runner.py`'s containment fix imports
  `_choose_slot`/`_CONFIRMED_PROVIDER_STATES` directly from
  `core.schedule_appointment` — names that do not exist in HEAD's committed
  version of that file (they are the in-flight session's own new helpers).
  Committing `async_runner.py`'s diff alone would raise an `ImportError`.
- `channels/direct_api/calcom.py`'s diff is a genuine mix of this session's
  fix (raise on upstream failure instead of returning `[]`) and the
  concurrent session's new `BookingOutcomeUnknown` exception handling in
  `book_slot`/`cancel_booking`, confirmed by that code's own test
  (`tests/unit/test_booking_retry_safety.py`).

Per the task's hard rule ("if those files are being actively modified,
commit what is stable and EXCLUDE the in-flight work... do not commit a
half-finished change"), all of it was excluded as a unit rather than
hand-split, because every attempted split point turned out to be a real
function call, not just adjacent prose. The **widened dead-monkeypatch
guard** (`tests/unit/test_a_stubbed_gate_is_actually_stubbed.py`) was
excluded for the same reason: its own self-consistency test
(`test_known_safe_collisions_are_still_present`) requires several of the
above new test files to exist in the tree, and it changed again 17 minutes
into this session, confirming it is still being edited live.

**None of this reopens anything.** These three fixes were never applied to
production; excluding them from this branch leaves production exactly as
exposed as it already was, no more and no less.

## A temporary, low-severity side effect of shipping fix 3 alone

`core/tool_auth.py`'s `IDENTITY_REQUIRED_READ_TOOLS` already lists
`get_conversation` as needing a key — that is the *intended end state*, once
the (currently blocked) ownership fix ships. Until it does, production's
`get_conversation` still accepts an anonymous/wrong-owner call, even though
this branch's website, registry catalogues and docs now describe it as
requiring one. This makes the docs *more conservative* than the live
behavior (an agent reading them would believe it needs a key it doesn't
strictly need yet) — not less safe. It should resolve itself the moment the
ownership fix ships; flagging it here so nobody mistakes "the docs now say
14" for "the hole is closed."

## The un-applied DB migration

`migrations/operations_table.sql` (adds an `appointment_id` column to
`operations`, keyed by the provider's own booking id, for the
cancellation-authorization lookup) is **not committed** in this branch — it
belongs to the blocked cancellation-authorization fix and referencing a
column no shipped code yet reads would be more confusing than useful. It
remains uncommitted in the working tree alongside the code that needs it.
Until both are applied together: `storage/outcome_store.py`'s (in-flight)
`get_appointment_owner_async` cannot look anything up by provider booking id
regardless, so this has no effect on anything in this branch. It only
matters once the ownership/cancellation-authorization branch ships — at that
point the migration must be applied to Supabase (SQL editor, same mechanism
as `migrations/enable_rls.sql`) *before or during* that deploy, not after,
or `get_appointment_owner_async`'s Supabase fallback will silently find
nothing for every row written before the column existed (it fails closed —
denies the cancel — rather than granting it, but authorized cancellations
of pre-migration bookings would incorrectly be refused until the column is
backfilled or the row is re-written).

## How to deploy this branch (when you decide to)

Production (`api.hatchloop.dev`) is a **Render** blueprint
(`deploy/render.yaml`, service `smb-broker`, `runtime: docker`,
`dockerfilePath: ./deploy/Dockerfile`) that auto-deploys on push to the
`main` branch of the GitHub remote. There is no separate deploy script to
run — the mechanism is git push.

1. Review the 2 commits on `security/honesty-release-20260921`
   (`43cb6dd`, `b332e25`) against `main`.
2. Merge (or fast-forward) `main` to include them, then push `main` to the
   GitHub remote. Render's blueprint watches that branch and builds
   `deploy/Dockerfile` automatically.
3. The edge (`hatchloop.dev/mcp/agent-broker` and friends) is a separate
   Cloudflare Worker that serves cached snapshots (`edge/src/snapshots/`)
   independently of the Render origin — this release does not touch that
   worker or its snapshots, so no edge redeploy is required for this
   specific change to take effect on the origin. The origin
   (`api.hatchloop.dev` / `hatchloop.dev` non-edge routes) picks it up on
   the Render deploy alone.

### Verify success after deploying

- `curl -fsS https://api.hatchloop.dev/health` → 200 (matches `ci.yml`'s own
  smoke check).
- `curl -s https://api.hatchloop.dev/keys/request -X POST -H 'Content-Type: application/json' -d '{"email":"you@example.com"}'`
  → expect `503 {"error":"onboarding_unavailable", ...}` **as long as
  RESEND_API_KEY remains unset on Render** (verify current state first via
  `curl -s https://api.hatchloop.dev/healthz/external` — look for
  `"resend": "not_configured"`). If Resend has since been configured, expect
  `200 {"status":"verification_sent"}` instead — either is correct, matching
  whichever is actually true; a `200` with no email sent, or the string
  "verification_sent" for a call that never reached Resend, is the failure
  mode this release exists to prevent.
- `curl -s https://api.hatchloop.dev/manifest` (or the MCP `tools/list` call
  used in the smoke job) and eyeball that the free-tier language/counts read
  "14 of 23" / "11 always-free", not "15"/"12" — confirms the new
  `core/tool_auth.py` derivation deployed.
- Run the CI workflow itself on the push (GitHub Actions on `main` will run
  it automatically) and confirm the `verify` job is green. Locally, this
  session ran every step of `.github/workflows/ci.yml`'s `verify` job
  against a clean worktree of this exact branch — see the session's CI
  results below.

### Roll back

A plain `git revert` of `b332e25` and `43cb6dd` (or a Render rollback to the
prior deploy) is **safe** with respect to the vulnerabilities named at the
top of this file: neither commit implements an authorization or ownership
check, so reverting them cannot reopen the unauthorized-read or
unauthenticated-cancellation holes — those were never closed by this branch
in the first place and stay exactly as they are regardless of whether this
branch is deployed or rolled back.

Reverting **does** bring back two real, live problems this branch fixes:
`POST /keys/request` will again return a false `200 verification_sent` on
every signup while Resend is unconfigured, and the published tool counts
will again read the stale "15 of 23 / 12 always-free" on the six surfaces
listed above. If you roll back, treat re-shipping this branch (or the
underlying fixes) as still outstanding, not resolved.

**Do not** treat rolling back *forward* to whatever state the working tree
is in outside this branch as a substitute rollback path — that tree also
still contains the concurrent, unfinished retry-safety edits described
above, and checking it out wholesale would ship a half-finished change
nobody has reviewed or run CI against.
