# MCP protocol revision 2026-07-28 on AgentBroker

> **Status: implemented on branch `feat/mcp-2026-07-28-20261003`, branched from 1f85885, which is the build
> that was live on 2026-10-03. It is NOT live until it is deployed through the gated wrapper.** Everything
> below describes the branch; until then the live server still answers `server/discover` with `-32601`.

AgentBroker speaks the 2026-07-28 revision of the Model Context Protocol **alongside** the older
`initialize` handshake. This page says exactly what that means, what we chose to be lenient about
and why, and what we do not implement. The code is `agent_interface/mcp_2026.py` (pure functions) wired
into `agent_interface/mcp_server.py` and `main.py`. Spec: https://modelcontextprotocol.io/specification/2026-07-28

## Why

Measured on 2026-10-03 (the HatchLoop demand review, which is kept outside this repo): 652 `server/discover` calls from 20
callers got `-32601` in 47 hours; 939 POSTs to the MCP doors (re-counted from the access log, 2026-09-29 to
2026-10-03; the review counted 934 a few hours earlier) already carried `MCP-Protocol-Version: 2026-07-28`.
The revision makes `server/discover` a server MUST and removes `initialize`, so a discover-first client could
not complete a handshake with us.

## Versions we speak

`server/discover` advertises, newest first: `2026-07-28`, `2025-11-25`, `2025-06-18`, `2025-03-26`,
`2024-11-05`. The last four are the **legacy** era (an `initialize` handshake). `initialize` negotiates only
those four: it never answers `2026-07-28`, because that revision removed the handshake.

## How the era of a request is decided

| The request has | Treated as | Notes |
|---|---|---|
| method `initialize` | legacy, always | headers and `_meta` that ride along are ignored |
| `_meta` with `io.modelcontextprotocol/protocolVersion: 2026-07-28` | modern, full validation | the client opted in |
| `_meta` naming a legacy version | legacy | served as it always was, unless the `MCP-Protocol-Version` header names the revision: `-32020`, HTTP 400 (the request contradicts itself) |
| `_meta` naming a version we do not speak | refused: `-32022`, HTTP 400 | `data.supported` lists ours |
| header `MCP-Protocol-Version: 2026-07-28`, no `_meta` | modern, **lenient** | see below |
| nothing | legacy | |

**Batches.** The revision's transport carries one request per POST. A JSON array in which any member carries the
modern `_meta` envelope is refused whole (`-32600`, HTTP 400, nothing dispatched): one set of HTTP headers cannot
mirror several bodies, so serving it would skip every header rule. A legacy batch, and a batch of header-only
requests, are served per member as before.

Header validation (`MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`) applies to modern requests only. A
legacy request is never header-validated: scanner-I sends an `Mcp-Method` header on 2025-06-18 requests
(about 11,000 in four days) and they must keep working.

### The three deliberate leniencies, and what each is based on

Measured from the production access log, 2026-09-29 to 2026-10-03 (counts only; see
`tests/fixtures/mcp_handshakes/scanner_shapes_observed_2026-10-03.json`):

1. **`initialize` is always legacy.** scanner-F, scanner-G and scanner-H send
   `MCP-Protocol-Version: 2026-07-28` with no `Mcp-Method` header, most likely with `initialize`.
2. **A 2026-07-28 header with no `_meta` envelope is served**, in the modern shape, with whatever headers it did
   send checked. scanner-B, scanner-C, scanner-D and scanner-E ask for `tools/list` that way and are served
   today; refusing them would break callers that work. The spec says a request missing `_meta` fields MUST be
   rejected. We follow it for any request that carries the envelope and relax it for the header-only shape.
3. **`server/discover` is answered for everybody**, with or without a version or an envelope, and without
   requiring `clientCapabilities`. Only an *unsupported* version on it is refused (scanner-A sends
   `1999-01-01` and expects exactly that).

## What each method returns to a modern request

Every successful result carries `resultType: "complete"` and `_meta["io.modelcontextprotocol/serverInfo"]`.
A capability door introduces itself as itself (`serverInfo.name` is the door), exactly as `initialize` does.

| Method | Extra fields | `cacheScope` | `ttlMs` |
|---|---|---|---|
| `server/discover` | `supportedVersions`, `capabilities`, `instructions` | public | 300000 |
| `tools/list` | | public (private + 0 when a failing key attaches `auth_warning`) | 300000 |
| `resources/list` | | public | 3600000 |
| `resources/templates/list` | `resourceTemplates: []` | public | 3600000 |
| `resources/read` | | public | 300000 |
| `prompts/list` | | public | 3600000 |
| `prompts/get`, `tools/call` | | none | none |

`tools/list` is short-lived because it annotates delivery channels from this deployment's configuration at
request time. The lists that are literals in the code can live for an hour. No list is paginated, so there is
never a `nextCursor`.

Capabilities we declare: `tools`, `resources`, `prompts`, every `listChanged` and `subscribe` flag `false`.
We omit `logging`: the revision deprecates it and we have no `logging/setLevel`.

## What a modern request is refused with

| Condition | HTTP | JSON-RPC code |
|---|---|---|
| version not one we speak | 400 | `-32022` `UnsupportedProtocolVersion`, `data: {supported, requested}` |
| `_meta` version not a non-empty string; `clientCapabilities` missing or not an object | 400 | `-32602` |
| `MCP-Protocol-Version` missing or different from `_meta`; `Mcp-Method` missing or different from the body; `Mcp-Name` missing, different from `params.name` / `params.uri` (Base64 sentinel decoded first), or present when the body has no string there | 400 | `-32020` `HeaderMismatch` |
| method we do not implement | 404 | `-32601` |
| unknown tool, bad arguments, unknown resource | 200 | `-32602` (a JSON-RPC error, not an envelope fault) |

Error messages name the header and the field, never the value (a header is attacker-controlled text).
`-32021` (`MissingRequiredClientCapability`) is never emitted: no tool needs a client capability.

## Not implemented, said plainly

- `subscriptions/listen`, `resources/subscribe`, `resources/unsubscribe`: no list changes at runtime, so there
  is nothing to subscribe to. A modern request for them gets `404` / `-32601`.
- The tasks extension (`tasks/get`, `tasks/update`, `tasks/list`): not advertised.
- `logging/setLevel` and the `logLevel` `_meta` key: logging is deprecated by the revision; we emit no log
  notifications.
- Multi round-trip requests (`resultType: "input_required"`): no tool asks the client for input.
- `x-mcp-header` tool annotations, completions, extensions.
- OAuth protected-resource metadata (`/.well-known/oauth-protected-resource`) - a separate piece of work.
- A GET stream or `DELETE` on the endpoint: `405`, as the revision says. `Mcp-Session-Id` is ignored, never
  minted or echoed.
- `ping` was removed by the revision. Legacy callers and the header-only shape still get an answer (monitors
  use it); a request carrying the revision's own `_meta` envelope gets `404` / `-32601`, as the spec says. It is
  the only removed method we keep, and `REMOVED_METHODS` in `mcp_2026.py` is the one place that says so.

## Compatibility with older clients

Verified two ways. (1) `tests/fixtures/mcp_handshakes/python_sdk_legacy_before_2026-07-28.json` is a real
recording of the official Python SDK client (mcp 1.26.0) against the commit *before* this change; the replay
test asserts the current server answers the same five requests with identical statuses and result shapes.
(2) Legacy responses are asserted to carry none of the new fields (`resultType`, `ttlMs`, `cacheScope`,
serverInfo in `_meta`); the legacy snapshots the edge worker serves are byte-for-byte what they were.

## Operations

- **No database migration.** Every new outcome row uses outcomes already accepted by
  `usage_events_insert_v2` (`ok`, `rpc_error`). New `error_code` labels: `unsupported_protocol_version`,
  `header_mismatch`, `invalid_meta`. A modern request's `detail` is `pv=2026-07-28` (after `door=<name>` when
  there is one); legacy rows keep their old text. The caller's name now comes from the request's
  `clientInfo` instead of a remembered `initialize`.
- **The live path is Caddy to the container**; the Cloudflare edge worker is not in it. The worker is changed
  only so that it cannot serve its frozen legacy-shaped `tools/list` to a modern client if it is ever put
  back (modern requests are proxied to the origin; CORS allows the new headers).
- **Post-deploy check:** `python scripts/probe_mcp_2026.py` runs eight read-only JSON-RPC checks (no tool call,
  no message) against `api.hatchloop.dev` and exits 0 only if all pass. Measured against build 1f85885 on
  2026-10-03 it passes 1 of 8 (only the legacy `initialize` check); against this branch run through a real
  uvicorn server it passes 8 of 8. To check the public door URLs instead:
  `--base https://hatchloop.dev/mcp/agent-broker --door-base https://hatchloop.dev/mcp`.
- After a deploy, the evidence to look for is in `usage_events`: `method = 'server/discover'` with
  `outcome = 'ok'`, and `method = 'server/discover' and outcome = 'rpc_error'` falling to zero except for
  deliberately bogus versions.
