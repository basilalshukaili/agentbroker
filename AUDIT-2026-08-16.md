## 1. Architecture map

Repo root: `C:\ai company\agentbroker` (github.com/basilalshukaili/agentbroker,
branch `main`, clean at `cd8526f`). Python 3.11+ FastAPI service (`main.py`,
**46 KB, 122 functions, 53 `@app.*` routes** — see coupling note below) fronted
by a Cloudflare Workers edge layer (`edge/`).

### `core/` — the 16 MCP operation handlers
One file per tool (`find_business.py`, `send_message.py`,
`schedule_appointment.py`, etc.), each a thin handler that validates input via
`core/models.py` Pydantic schemas, runs `compliance/pre_check.py`, dispatches
to a `channels/*` adapter, and records via `billing/durable_meter.py`. Two
tools are new since the last audit: `check_booking_link.py` and
`check_compliance.py` (both added Aug 13/16, both free/read-only pre-flight
checks) — **registered in code and covered by tests, but not live in
production** (see Finding #2). Handler code itself is clean, consistent,
well-separated per-tool.

### `channels/` — outbound delivery adapters
`sms_email/{twilio_sms,sendgrid_email,resend_email}.py`,
`voice_ai/vapi.py`, `direct_api/calcom.py`,
`browser_automation/playwright_adapter.py`, gated by
`channels/stub_policy.py` (the Aug-4 fix that killed fabricated-success
responses — confirmed still in place, no regression). `channels/web_form/`
is an **empty stub** — only `__init__.py`, no adapter implementation; it's an
unfinished channel that exists in name only. `sendgrid_email.py` is still
imported live (`core/send_message.py`, `core/send_transactional_confirmation.py`)
as a fallback behind Resend — not dead, just secondary.

### `supply/` — SMB directory
`smb_directory.py` (31 demo businesses per memory — not independently
re-verified this pass) + `booking_page_importer.py` (backs the
`import_booking_url` tool). Small, single-purpose, no issues found.

### `billing/`
`meter.py` (in-memory) → `durable_meter.py` (Supabase fire-and-forget wrapper,
confirmed live, see Finding #5) → `polar_webhook.py` (signature verify +
event dispatch) → `agent_interface/identity.py` (JWT mint). `x402_gate.py` and
the edge's `x402.ts` are **intentionally dormant** (`X402_RECEIVER_ADDRESS`
unset) — correctly a no-op per design, not a bug, but it's real complexity
(251 lines in `x402.ts` alone) kept alive for a payment rail the memory's own
"Don'ts" list says not to activate. `pricing_tiers.py` and `providers.py` are
wired into `main.py` and used.

**Bug found in `polar_webhook.py`:** `handle_polar_event()` treats both
`order.paid` and `order.created` as grant events
(`_GRANT_EVENTS = {"order.paid", "order.created", "subscription.active", "subscription.created"}`)
with **no idempotency guard on order/customer id** — nothing stops the same
underlying purchase from minting two tokens and sending two emails if both
events fire (normal for most payment processors). This is compounded by a
second, live issue found in Polar's dashboard (not the repo): **two active
webhook endpoints both point at `/webhooks/polar`** —
`0c5f11b5-…` (created 2026-08-04, matches the current `POLAR_WEBHOOK_SECRET`)
and a second, older one, `44dd37a0-…`, **created 2026-05-31**, never
deactivated. If that stale endpoint's secret ever matches, or gets
regenerated against the wrong ID, a single $9 purchase could double-fire.
Low current risk (mismatched secret likely just fails silently) but it's
undocumented cruft nobody flagged.

### `agent_interface/`
`mcp_server.py` (the JSON-RPC dispatcher, builds `tools/list` from
`manifest/manifest.json` via `manifest_server.get_full_manifest()`),
`identity.py` (JWT issue/verify/revoke), `discovery.py`, `well_known.py`,
`webhooks.py` (inbound registration, wired into `main.py`), `self_test.py`
(confirmed live: 6/6 passing right now). No dead code found here.

### `compliance/`
`pre_check.py` is the single non-bypassable gate every send-type tool routes
through; `jurisdiction_rules.py` (22 jurisdictions per memory),
`consent_store.py`, `audit_log.py`, `retention_policy.py`,
`content_classifier.py`, `log_redactor.py`, `recording_consent.py`,
`campaign_registry.py` (marked in its own docstring as "10DLC campaign
registry **scaffold**" — i.e. self-declared incomplete). All wired, no
orphans found.

### Coupling note
`main.py` is a 46 KB / 122-function / 53-route monolith that every other
package (`core/`, `channels/`, `billing/`, `compliance/`, `agent_interface/`)
funnels through as the single FastAPI entry point. Nothing is broken by this,
but it's the widest blast-radius file in the repo — any change here risks
every route at once, and it's the natural place future regressions will hide.
Not urgent, but worth a decomposition pass before the codebase grows further.

### Manifest/snapshot staleness (root cause of Finding #2's symptoms)
Tool metadata flows: `manifest/manifest.json` (hand-declared, 78 KB) →
`agent_interface/manifest_server.get_full_manifest()` → `mcp_server._build_tool_list()`
→ served live by Render. Separately, `edge/src/snapshots/mcp-tools-list.json`
is a **frozen copy** baked into the Cloudflare Worker bundle at build time (so
the edge never has to call origin for `tools/list`). `manifest.json` was
regenerated 2026-08-13 (16 ops, correctly includes the two new tools) but the
**edge snapshot was last regenerated 2026-08-04** (`git show --stat 642795d`)
and was never rebuilt after. Since Render itself is also stuck on the 2026-08-04
deploy (Finding #2), the edge snapshot and the live origin happen to agree on
"14 tools" right now — but that's coincidence, not sync: they're two
independently stale artifacts that will diverge the moment either one is
redeployed alone.

## 3. The edge-worker ownership question — full trail

**What we can prove we own:** Cloudflare account `Lordbasil147@gmail.com's
Account` (id `8f0ebd0046e3f1c8a506f8f0f6d9476f`) — confirmed via
`npx wrangler whoami` from `edge/`, which returned exactly this one account,
authenticated via a cached OAuth token with `workers:write` scope. Its
workers.dev subdomain is `techmate` (i.e. it can only ever publish to
`*.techmate.workers.dev`). `edge/wrangler.toml` has `account_id` hard-locked
to this ID since commit `1d547b2` (2026-08-13, "lock account_id for edge
rate-limit deploy"). We can redeploy `techmate.workers.dev` at will — it just
did not have the freemium rate-limiter or any commit past 2026-08-13.

**What we cannot touch:** `agent-broker-edge.basil-agent.workers.dev`. A
Cloudflare workers.dev subdomain is chosen per-account and globally unique —
the fact that it resolves to a *different* subdomain than our one
authenticated account (`techmate`) proves it is provisioned under a
*different* Cloudflare account. Grepped the entire repo, `.wrangler/cache`,
every `.env*`, and every doc file for any account ID, API token, or login
tied to "basil-agent" — **none exists anywhere in the codebase.** There is no
`wrangler.toml` targeting it, no cached credential, no CI secret name that
references it.

**Yet it is the one thing that matters most:** it's the URL in
`glama.json`'s `remotes[0].url`, it's what `agent_interface/discovery.py` and
`config.py` hardcode as `PUBLIC_BASE_URL`/support/docs URLs by default, and
— most tellingly — it's the literal live value of `MCP_PUBLIC_URL` in the
Render backend's own production env vars right now (`https://agent-broker-edge.
basil-agent.workers.dev/mcp`, confirmed via the Render API). Smithery's public
listing also still points here. In other words: **every discovery surface the
project ships treats an account we can't authenticate to as canonical**, while
the one edge deployment we actually control (`techmate.workers.dev`) is
effectively an orphan that gets none of the real Smithery-routed traffic.

**Repo docs actively conflict with each other on this point** — not just
stale, contradictory in the same file:
- `HANDOFF.md` line 4 calls `basil-agent.workers.dev` the "Primary URL," then
  line 5, one line later, says "All … `basil-agent.workers.dev` references in
  this doc are historical — ignore them."
- `LAUNCH_STATUS.md` line 9 marks it "✅ Live," while line 13 of the *same
  file* marks the identical string "❌ NXDOMAIN — not in use."

These read as artifacts from different points in the project's build history
(Fly.io → Koyeb → Cloudflare migrations) that were never reconciled, not as
a deliberate current design. There is no way, from the repo alone, to tell
who set up `basil-agent.workers.dev` or when.

**What "full ownership" would require going forward:** either (a) recover
credentials/account access for whatever Cloudflare account owns the
`basil-agent` subdomain — check the Cloudflare account tied to
`lordbasil147@gmail.com`'s browser/dashboard login (as opposed to the
`wrangler`-cached API token, which only sees one account — a dashboard login
can be a member of multiple accounts that an API token wouldn't enumerate),
or (b) formally cut over: redeploy the current `techmate.workers.dev` build
(already ahead — has the rate limiter) as canonical everywhere (Smithery
listing URL, `glama.json`, `MCP_PUBLIC_URL`/`PUBLIC_BASE_URL` env vars,
`config.py` defaults), and let `basil-agent.workers.dev` go stale on
purpose. The founder gate for exactly this (`agentbroker-smithery-url` in
`founder_gates.json` per memory) is already open and waiting on a ~2-minute
manual Smithery dashboard edit — that's the cheapest unblock, but it does not
by itself resolve *ownership* of the old subdomain, only *traffic routing*
away from it.

## 5. Fulfillment chain: paid order → token mint → email

**Code path unchanged and structurally sound** since the 2026-08-04
end-to-end proof: `billing/polar_webhook.py` verifies the Standard Webhooks
signature → `agent_interface/identity.issue_subscription_token()` mints a JWT
→ `billing/telegram_revenue_alerts.send_api_key_email()` emails it via Resend
→ a Telegram revenue alert fires. Nothing in this path has rotted at the code
level; tests pass (152/152, see below).

**What has changed since Aug 4 is entirely on the "does anyone actually use
it" side:**
- Polar order history for the AgentBroker product shows **exactly one order,
  ever** (`b2df49af…`, 2026-08-04, $8.57 after currency, `basilalshukaili@
  gmail.com`) — and its current status is **`refunded`**. There is no
  evidence the refund broke anything technically (the token issued at
  purchase time isn't automatically revoked by a Polar-side refund unless
  something explicitly listens for `order.refunded`/`subscription.revoked` —
  **not currently in `_GRANT_EVENTS` or handled anywhere in
  `polar_webhook.py`**, i.e. a refunded customer's token would keep working
  until natural 90-day expiry. Minor gap, not urgent given current volume,
  but worth a line: **there is no revocation-on-refund path.**
- Two live webhook endpoints registered against the same URL (see §1 bug
  note) — the older one (2026-05-31) should be deleted as cleanup.
- `total_payment_attempts: 0` on the live metrics counter despite ~8000
  completed operations — the auth gate is working exactly as designed
  (blocking unauthenticated writes), it's just that nobody has hit it and
  converted since the founder's own test.

**Test suite:** ran `python -m pytest -q` live during this audit —
**152 passed, 0 failed**, matching the 4331159 commit message
("Tests 139->152 pass"). README's test-count badge still says "103/103" —
stale by at least 49 tests, cosmetic only.
